## Product design

### Goals / Non-goals

**Goals (v1):**
- Let an MCP-compatible agent inspect a tenant's Vercel projects and deployments (list/get), and read deployment build/runtime events — the read-only "what is deployed, is it healthy" surface.
- Let the agent perform the operational actions a human admin routinely does from the Vercel dashboard: trigger a new deployment, cancel one in flight, promote/roll back production traffic to a given deployment, and delete a deployment.
- Let the agent manage a project's custom domains and the DNS records Vercel hosts for them (list/add/remove domain; list/create/delete DNS record).
- Let the agent manage a project's environment variables (list — metadata only; create; delete) without ever being able to read back a decrypted secret value through this connector.
- Every call carries the tenant's own Vercel credential from the gateway-supplied request header and is scoped to that tenant/team only — this ticket's "credentials encrypted and every action logged" promise is satisfied by complying with the platform's existing Header/audit-log contract, not by building new infrastructure.

**Non-goals (v1 — follow-up ticket if a concrete need shows up):**
- Vercel Sandboxes, Feature Flags, AI Gateway, Marketplace integrations, billing/usage, KMS, access groups, networking/firewall rules, log drains, Checks/CI, build artifacts, web analytics, microfrontends, rolling releases, team/organization administration, project transfer, project avatar upload. These are large additional surfaces the ticket does not ask for; see "Decisions made by DEV01" for why they are deferred rather than guessed at.
- Reading back a decrypted environment-variable value (Vercel's `GET /v1/projects/{idOrName}/env/{id}` with `decrypt=true`). This is a deliberate security exclusion, not an oversight — see "Decisions made by DEV01".
- Creating or deleting a Vercel *project* itself (only managing deployments/domains/DNS/env vars of projects that already exist). Project lifecycle is a separate, lower-frequency admin action; deferred.

### Acceptance criteria AC1..AC13

- AC1: Given a valid Vercel access token in the request header, When the agent calls `vercel_list_projects`, Then it returns the tenant's (or team's, if a team id header is present) Vercel projects — name, id, framework, latest production deployment — without any other credential.
- AC2: Given a project id or name, When the agent calls `vercel_list_deployments` for it, Then it returns deployments (id, url, state, target, created time) newest first, capped by the tool's `limit` parameter (default ≤ 50, hard cap ≤ 200 — never unbounded).
- AC3: Given a project and a git ref (or an explicit file set), When the agent calls `vercel_create_deployment`, Then Vercel starts a new deployment and the tool returns its id, url, and initial state.
- AC4: Given a deployment that is queued or building, When the agent calls `vercel_cancel_deployment`, Then Vercel stops it and the tool reports the resulting state; calling it again on a deployment that already finished (or does not exist) returns the structured error envelope, not a crash or a raw Vercel error passthrough.
- AC5: Given a project and a deployment id that belongs to it, When the agent calls `vercel_promote_deployment`, Then production traffic for that project points at the given deployment and the tool confirms the new production deployment id (this single tool covers both "promote a new deployment" and "roll back to a previous one" — the Vercel call is the same shape either way).
- AC6: Given a project, When the agent calls `vercel_list_domains` / `vercel_add_project_domain` / `vercel_remove_project_domain`, Then the project's custom domains reflect the change, and adding a domain that is already verified/attached elsewhere returns a structured error rather than a silent no-op.
- AC7: Given a domain already attached to a project through this connector, When the agent calls `vercel_list_dns_records` / `vercel_create_dns_record` / `vercel_delete_dns_record`, Then Vercel's DNS zone for that domain reflects the change.
- AC8: Given a project, When the agent calls `vercel_list_env_vars`, Then it returns variable name, target environments, and type — and the response never contains a decrypted `value` field, regardless of what the Vercel API itself returns for that call.
- AC9: Given a project, When the agent calls `vercel_create_env_var` with name/value/target, Then Vercel stores it and the tool's response confirms id, name, and targets — never echoing the value back; `vercel_delete_env_var` removes a variable by id.
- AC10: Given the request is missing the Vercel access-token header, When any tool is called, Then the service returns HTTP 401 with a body listing the required header(s) — not a 500 and not a Vercel-API passthrough; given a well-formed request for which the Vercel API itself returns an error (404 / 429 / 5xx / network timeout), Then the tool returns the structured error envelope with the matching code (`not_found` / `rate_limited` / `upstream_error`) and never raises an unhandled exception.
- AC11: Given a request with only the access-token header, calls operate on the token owner's personal Vercel account; given a request that also carries the team-id header, calls operate on that team's resources instead — and under concurrent requests from different tenants, no response, log line, or cached state ever mixes one tenant's token/team/data into another tenant's call (multi-tenant isolation is a hard requirement on this platform).
- AC12: Given any destructive tool (`vercel_cancel_deployment`, `vercel_delete_deployment`, `vercel_remove_project_domain`, `vercel_delete_dns_record`, `vercel_delete_env_var`) is listed via `tools/list`, Then it is annotated `destructiveHint: true`, accepts only an explicit resource id (never a filter, wildcard, or "all" argument), and read-only tools are annotated `readOnlyHint: true`.
- AC13: Given the service is otherwise running, When `GET /health` is called without any credential header, Then it returns `200 {"status":"ok"}` purely from a local check — it must not depend on reaching `api.vercel.com` (so the gateway's container healthcheck does not flap on a Vercel outage).

## Tech design

### Conclusion

Build a new Python 3.12 / FastMCP service in the already-created `MSPbotsAIFramework/vercel-mcp` repo (empty scaffold today), following the house `vendor-mcp-development` SOP: Streamable HTTP `/mcp` + local-only `GET /health`, credentials read per-request from `X-Vercel-Access-Token` (required) and `X-Vercel-Team-Id` (optional) headers via `contextvars`, 19 tools grouped by Vercel resource (projects / deployments / domains / DNS / environment variables), structured JSON error envelopes, and the fixed README/Dockerfile/test-layout the SOP requires. This is the simplest possible shape for the requirement: Vercel's REST API already maps cleanly onto "one tool per admin action", there is no orchestration across other vendors, and no UI work — the connector detail/connect-form UI is the platform's existing generic surface, driven by the `credential_fields` this repo registers.

### Where the current implementation lives

Nowhere yet. `README.md:1-2` is the entire repo content (two lines, no code). This is a from-scratch build against Vercel's public API, not a change to existing logic.

| Option | Approach | Pros | Cost | Verdict |
|---|---|---|---|---|
| Mirror the full Vercel REST surface 1:1 | Expose all 349 OpenAPI paths as tools | Nothing is "missing" | Breaks the SOP's ≤20-tools cap and token-economy rules (§A4) outright; most of the surface (sandboxes, billing, KMS, CI checks, analytics...) is operational/low-value for an agent and would bury the useful tools in noise | Rejected |

| **Five-resource slice: projects, deployments, domains, DNS, env vars (chosen)** | 19 tools covering the day-to-day admin surface | Matches the SOP's ≤20-tool cap with room to spare; covers the full "ship it and point a domain at it" loop a human admin does from the dashboard; every endpoint picked has a public, stable OpenAPI definition (no guessing at behavior) | Still omits several large areas (see Non-goals) — explicitly deferred, not silently dropped | **Chosen** |

Tech stack is not a choice point: every MSPbotsAIFramework vendor MCP uses Python 3.12 + `uv` + FastMCP (SOP §A3/§9) — "no alternative: this is the house convention for every vendor MCP repo in this org, and deviating would make the repo inconsistent with the other ~70 repos the gateway already talks to."

### Data & API contract

**Transport**: `POST /mcp` (Streamable HTTP, `stateless_http=True`); `GET /health` → `200 {"status":"ok"}`, no upstream dependency (AC13).

**Credential headers** (read per-request, never persisted — SOP §3.1):

| Header | Required | Forwarded to Vercel as | Meaning |
|---|---|---|---|
| `X-Vercel-Access-Token` | yes | `Authorization: Bearer <token>` | Vercel personal or team access token (Vercel dashboard → Account Settings → Tokens) |
| `X-Vercel-Team-Id` | no | `teamId=<value>` query param on every call | Scopes all calls to a Vercel team; omit to use the token owner's personal account (AC11) |

Missing `X-Vercel-Access-Token` → `401 {"error": "missing required header(s)", "required": ["X-Vercel-Access-Token"]}` (AC10).

**Tools** (19 total, upstream = `https://api.vercel.com`; every tool also accepts the implicit `team_id` from the header above):

| Tool | Upstream endpoint | Key params | Hints |
|---|---|---|---|
| `vercel_list_projects` | `GET /v10/projects` | `limit` (≤50 default/≤200 max), `search` | `readOnlyHint` |
| `vercel_get_project` | `GET /v9/projects/{idOrName}` | `project_id_or_name` | `readOnlyHint` |
| `vercel_list_deployments` | `GET /v7/deployments` | `project_id`, `target`, `state`, `limit` | `readOnlyHint` |
| `vercel_get_deployment` | `GET /v13/deployments/{idOrUrl}` | `deployment_id_or_url` | `readOnlyHint` |

| `vercel_cancel_deployment` | `PATCH /v12/deployments/{id}/cancel` | `deployment_id` | `idempotentHint` (AC4) |

**Error envelope** (returned by every tool on an upstream failure — never a raw passthrough or unhandled exception, AC10):

```json
{"error": {"code": "not_found", "message": "deployment dpl_xxx not found", "retryable": false}}
```

`code` ∈ `not_configured` | `unauthorized` | `not_found` | `invalid_argument` | `rate_limited` | `upstream_error` (fixed vocabulary, SOP §4). Empty result sets return an empty list, never `not_found`.

**Vendor registration** (`credential_fields` for `mcppub register`, review leg uses this verbatim at publish time):

```json
{
  "X-Vercel-Access-Token": {"label": "Access Token", "type": "password", "required": true, "description": "Vercel personal or team access token (Vercel dashboard -> Account Settings -> Tokens)", "example": "AbCdEfGh123..."},
  "X-Vercel-Team-Id": {"label": "Team ID", "type": "str", "required": false, "description": "Vercel team id to scope calls to a team (omit to use the token owner's personal account)", "example": "team_1a2b3c4d"}
```

This also drives the platform's generic connect-form (wiki: `ProductDocs/_connector-fields.md` "Variant 1 — credential form" — one masked secret field + one plain optional field, same shape as the wiki-documented N-able RMM / SentinelOne forms); no platform-side UI change is needed.

### Non-functional

- **Idempotency & concurrency**: credentials and team scope live in `contextvars`, set per request and reset in `finally` — no global/module-level state ever holds a token (SOP §3.3/§3.4, AC11). Write tools (`create_deployment`, `add_project_domain`, `create_dns_record`, `create_env_var`) are **not** idempotent because Vercel's API has no `Idempotency-Key` mechanism (confirmed: 0 mentions in the OpenAPI spec) — a blind retry on a transient network error can create a duplicate deployment/domain/record/env-var on Vercel's side. This is a known constraint of the upstream API, not a gap in this design; the client only auto-retries on 429/5xx for *read* calls and for the cancel/delete/promote calls that are inherently idempotent on Vercel's side (re-canceling/re-deleting/re-promoting the same target is a safe no-op or a clean `not_found`).
- **Performance**: outbound connect/read timeouts 5s/30s; single logical tool call budget < 120s including retries (SOP §5); list tools default to `limit=50`, hard-capped at 200, to keep responses within the ~20000-character token-economy budget (SOP §A4).
- **Security**: credentials only ever come from the two headers, never env/config/log; `vercel_list_env_vars` strips any decrypted value unconditionally regardless of what Vercel returns, and the service never requests `decrypt=true` (AC8) — this is enforced in code, not just by convention, and is covered by an automated test against a mocked upstream that *does* include a value, so the stripping can't silently regress. `gitleaks detect` runs before delivery (no real tokens ever committed; `.env.example` uses placeholders).
- **Multi-tenant isolation**: one container instance serves every tenant concurrently; the per-request `contextvars` pattern plus "never use a module-level HTTP client holding credentials" is the enforcement mechanism (AC11), covered by `tests/test_middleware.py`'s concurrent-request test.
- **Observability**: structured error envelope makes failures classifiable by `code` without parsing free text; the platform gateway (not this repo) is the system of record for the per-call audit log (Current state, "already exists" citation) — this repo's logs are limited to its own operational logging (startup, unhandled-exception traces that never reach the client), never request bodies/tokens.

### Risks & dependencies

- **Risk — scope mismatch**: v1's 19-tool scope is DEV01's own judgment call, not something the ticket specified. Mitigation: documented explicitly in Open questions and "Decisions made by DEV01" so Product can redirect with a single comment; does not block shipping.
- **Risk — no upstream idempotency**: retrying a failed `create_deployment`/`create_dns_record`/`create_env_var`/`add_project_domain` call can create a duplicate on Vercel's side. Mitigation: the HTTP client does not auto-retry these specific write calls on ambiguous failures (only on a clean "upstream never received the request" case such as a connect-timeout before any bytes were sent); documented in README for anyone calling the tool directly.
- **Risk — secret handling in `create_env_var`**: the tool necessarily receives a plaintext secret value as a tool argument (MCP has no secret-argument channel). Mitigation: the value is never logged, never echoed back in the response, and never cached; this is the same constraint every credential-form connector already has (the platform's "Protected" promise covers transport/storage, not what an agent chooses to pass as an argument) — not something this design can fully close, flagged here rather than silently assumed away.
- **Dependency — none on other tickets.** No other MSPbotsAIFramework repo, platform repo, or in-flight PRD needs to land first or after this one; `Track: vendor-mcp` is a single-repo change.
- **Dependency — GitHub App permissions**: the org-admin repo creation that unblocked this ticket (Current state) does not grant DEV01 `administration` on MSPbotsAIFramework going forward — any *future* new-repo need will hit the same wall. Not a blocker for this ticket (the repo already exists), but worth the reviewer knowing it isn't fixed at the root.

### Decisions made by DEV01

No one was available to ask (unattended design tick), so the following first-version choices were made by DEV01 and are each reversible with one comment on this ticket:

- **Scope = projects + deployments + domains + DNS + environment variables (19 tools)**, not the full 349-endpoint Vercel surface. Why: matches the SOP's ≤20-tools cap and token-economy rules, and covers the complete "ship something and point a domain at it" loop an admin does by hand. Alternative not chosen: a narrower deployments-only slice (rejected — see Option analysis) or mirroring everything (rejected — breaks the tool-count cap).
- **`vercel_promote_deployment` covers both "promote" and "rollback"** instead of shipping two near-identical tools (Vercel's own `POST /v1/projects/{projectId}/rollback/{deploymentId}` and `POST /v10/projects/{projectId}/promote/{deploymentId}` do almost the same thing: point production at a given deployment id). Why: one tool, one mental model for the agent ("point production at deployment X" — if X is an older one, that *is* the rollback); keeps the tool count down. Alternative not chosen: exposing Vercel's separate rollback endpoint as its own tool — rejected as redundant.
- **No decrypted environment-variable value can ever be read back through this connector**, even though Vercel's API supports it (`?decrypt=true`). Why: this is the single most sensitive piece of data in a Vercel account (production secrets, DB credentials, API keys) and an agent that can read it back can exfiltrate it into a chat transcript; write-only (create/delete) is enough for "manage config" without that exposure. Alternative not chosen: exposing a read with a scary warning in the description — rejected, because an agent cannot reliably self-police a capability it has been given; the safer boundary is to not grant it.
- **Credential header split: one required secret (`X-Vercel-Access-Token`), one optional plain field (`X-Vercel-Team-Id`)**, not a single combined field. Why: matches Vercel's own API shape (token + optional `teamId` query param) and the wiki's documented "credential form" convention (one masked field + plain fields), so the generic connect-dialog renders sensibly without any platform-side special-casing.
- **No OAuth.** Vercel does expose an `oauth2` security scheme in its OpenAPI spec, but the SOP's `/api/vendor-register` only supports header-keyed credentials, and a personal/team access token is the documented, simplest path for a server-to-server integration like this one. Why not OAuth: it would need the exact "needs OAuth or special credential handling" manual-registration path the SOP explicitly steers away from for a first version, with no corresponding capability gain for this use case.

To change any of these, say so in a comment and move the ticket back to `5b - ready for groom`.

## Self-test

### Implementation vs. tech design — deviations

- **`vercel_cancel_deployment` is annotated `destructiveHint: true` in addition to `idempotentHint: true`.** The "Data & API contract" table above lists its Hints as `idempotentHint (AC4)` only, but AC12 explicitly names `vercel_cancel_deployment` as one of the tools that "is listed via `tools/list` ... annotated `destructiveHint: true`". AC12 is the pass/fail statement, so the implementation follows AC12; this is a one-line inconsistency in the contract table above, not a scope change. `tests/test_tools.py::test_tool_list_annotations_match_contract` asserts the AC12 wording.
- **DNS-rebinding protection**: the tech design's Change list references `TransportSecuritySettings(enable_dns_rebinding_protection=False)` (SOP §7) as something to configure explicitly. The installed stack (`fastmcp==2.14.7`, `mcp` SDK bundled with it) does not expose a parameter to pass `TransportSecuritySettings` through `FastMCP.http_app()` — read the source (`fastmcp/server/http.py::create_streamable_http_app`, `mcp/server/streamable_http_manager.py`) to confirm: `StreamableHTTPSessionManager` is built without a `security_settings` argument, and `mcp/server/transport_security.py::TransportSecurityMiddleware.__init__` defaults to `enable_dns_rebinding_protection=False` precisely "for backwards compatibility" when none is supplied. So DNS-rebinding protection is already off by default in this dependency version; no additional code was needed. Re-verify this if `mcp`/`fastmcp` are ever upgraded — the default could change.
- **lifespan wiring**: `FastMCP.http_app()` in this version does not accept a `routes` kwarg (even though the private `create_streamable_http_app()` it calls does), so `/health` could not be added as an extra route on the same app instance the design assumed. Implemented instead as the officially-documented pattern (and the exact fix fastmcp's own `RuntimeError` message describes): an outer `Starlette` app with `routes=[Route("/health", ...), Mount("/", app=mcp_app)]` and `lifespan=mcp_app.lifespan` set explicitly. Verified this avoids the "Task group is not initialized" pitfall (SOP §7) — see Gates below.
